# Print estimates & open in slicer

Three slicer-related features live on the model page: **print estimates** (how
long a file takes and how much filament it uses), **open in slicer** (hand a
file straight to Bambu Studio or OrcaSlicer) and **push from slicer** (send the
file you just sliced back, as a new revision).

## Print estimates

Estimates come from **two** sources, depending on whether the file was already
sliced:

- **Already-sliced files carry their own numbers.** A `.3mf` exported from Bambu
  Studio or OrcaSlicer embeds per-plate print-time and filament predictions in
  its `Metadata/slice_info.config`. Print Vault reads these **directly out of
  S3** without a full download — it uses ranged GETs against the zip's index to
  pull only the bytes it needs.
- **Unsliced files are sliced on the server.** A `.3mf` with no embedded
  predictions is sent to the optional **slicer service** — a thin wrapper around
  the headless OrcaSlicer CLI — which slices it and reads the print time and
  filament use from the result, exactly as if you had pressed "Slice all" in
  OrcaSlicer.

The estimate shown is the **total across all plates** in a multi-plate project.

### How server-side slicing picks settings

The slicer service honors the settings **embedded in the file** rather than
guessing:

- **Bambu Studio and OrcaSlicer projects** are sliced as they are — with the
  project's own printer, process and filament settings and its own plates.
  OrcaSlicer is a fork of Bambu Studio and reads these projects natively, so
  the estimate lands very close to what Bambu Studio itself shows. Empty plates
  are skipped.
- **PrusaSlicer projects** are sliced with the generic profile below, overlaid
  with the project's layer height, walls, infill, speeds, accelerations,
  machine limits and the filament of the extruder the objects use. Only a
  whitelist of settings carries over, so a crafted archive can't smuggle
  anything else in.
- **Files with no settings** (a plain `.3mf` from CAD, Onshape, OpenSCAD, …)
  use a generic profile — by default a **Bambu Lab P1S, 0.4 mm nozzle, 0.20 mm
  Standard, Bambu PLA Basic**; your instance can pick another printer (see
  [configuration](/configuration#slicer-service-printer)). The file card says
  which printer such an estimate assumed ("Bambu Lab P1S … · generic profile").

Post-processing scripts in a project are never run. Projects from a newer Bambu
Studio than the bundled OrcaSlicer can contain settings it doesn't understand
(new "auto" values, start G-code using newer placeholders); those few settings
are reset to OrcaSlicer's defaults so the file still gets an estimate. For
multi-colour prints that can leave out filament-change time.

### Re-running slicing on a file

Every `.3mf` row in the create and edit forms has a **⟳ button** that decides
whether that file goes to the slicer when you save:

- **Files you are adding start queued** (⏳) — the same thing an upload does
  anyway. Click to take one out if you don't want an estimate for it; it is
  then stored with no estimates at all.
- **Files already on the model start out of the queue.** Click to queue one:
  its print time, filament weight and printer info are re-read from scratch.
  Use it to retry a file that failed to slice, to pick up a file you replaced
  outside Print Vault, or to **backfill newly added details onto older models**
  — filament colours and the multi-colour/multi-nozzle badges, for instance,
  only appear on files parsed since that shipped.

Nothing happens until you press **Save changes**; the icon shows an hourglass
for what the save will hand over, and clicking again undoes it. The old
estimates stay on the page until the new ones land. For files sliced in Bambu
Studio or OrcaSlicer this is quick and doesn't need the slicer service at all —
Print Vault re-reads the numbers the file already carries.

### Things to know about estimates

- **Hover the print time to see which slicer produced it.**
- **They are slicer predictions**, not your printer's firmware — the same kind
  of number Bambu Studio or OrcaSlicer shows. Bambu/Orca projects sliced on the
  server use the file's own settings and land within a fraction of a percent
  of what your slicer reports, so they're shown plainly.
- **A `~` marks an estimate that had to assume something:** a file without
  printer settings (estimated for the generic printer), a PrusaSlicer project
  (its settings translated to OrcaSlicer), or a project from a newer Bambu
  Studio whose custom G-code OrcaSlicer couldn't read (so it was left out).
  Treat those as ballpark figures.
  Files estimated before this distinction existed keep their `~` until they
  are re-sliced.
- **Unsliceable files are flagged.** If OrcaSlicer can't slice a file, the
  model page marks it — a useful signal that the file may be broken or
  unprintable, not silently missing an estimate. A model that is too big for
  its printer says so instead, naming the printer and its build volume
  ("Doesn't fit on the Bambu Lab P1S (256 × 256 × 250 mm)") — it may well fit
  a larger one.
- **Multi-colour prints are called out.** The filament badges show one swatch
  per slot the file actually prints from, in the colours the project was sliced
  with, plus a `multi-color` or `multi-material` badge when **a single plate
  changes filament mid-print** — the case that needs an AMS/MMU (or manual
  swaps). A project whose plates each print one different colour doesn't get
  it: each plate is its own print. This comes from the sliced result, so files
  estimated before it shipped fall back to "uses more than one filament" until
  they are re-sliced. A `multi-nozzle` badge means the print needs a printer with two nozzles
  (an H2D, Prusa XL or other toolchanger) — colours fed through a single nozzle
  by an AMS or MMU don't get it, since those are a filament swap rather than
  hardware you either have or don't. Files sliced before this shipped show the
  older plain filament badges until they are re-uploaded or re-synced.
- **Stale filament assignments are flagged.** If a file's objects point at a
  filament slot the project no longer defines (say, everything still on AMS
  slot 5 after the project was cut down to one filament), the model page shows
  a warning instead of a material badge. Open the file in your slicer and check
  which filament each object uses before printing; it isn't guessed, because the
  fallback could be a different material entirely.
- **The build plate is drawn at real size.** Alongside the estimate, the file's
  hardware context is recorded (printer model, nozzle, build plate, filaments,
  whether the project prints support material — shown as a `supports` badge —
  and the physical bed dimensions parsed from the file or a known-printer
  lookup) and used to render the 3D preview's plate at true dimensions. A
  dropdown in the preview lets you swap in another common plate (A1 mini, the
  X1/P1/A1 family, H2D, Prusa, Creality, Voron, …) to check whether the model
  would fit a different printer; the plate turns red when the model overflows
  it. The picker defaults to the printer the file was sliced for.
- **Slicing runs in the background** after upload, so it never blocks saving a
  model; the estimate appears once slicing finishes.
- **Some files are skipped:** legacy `.step` files (from before Onshape imports
  switched to `.3mf`) and files uploaded before the feature existed.
- **The service is optional.** Without `SLICER_URL`
  ([configuration](/configuration#optional-services)), unsliced files simply
  show no estimate and stay pending — already-sliced files still show their
  embedded numbers, since those don't need the service.

## Open in slicer

For any `.3mf`, the file menu offers **Open in OrcaSlicer** and **Open in Bambu
Studio** as an alternative to downloading — a one-click handoff via each app's
custom URL scheme. The link is token-authenticated (the slicer apps fetch it
themselves, without your browser's session cookie), so it works without exposing
the file publicly.

A few realities are worth knowing, because they come from how the two apps
behave, not from Print Vault:

- **Deep links are `.3mf`-only.** Bambu Studio rejects other filenames, so
  `.scad` and `.step` files show a plain download button instead.
- **The "not from a trusted site" prompt is expected.** Bambu Studio only
  auto-trusts MakerWorld and a few CDN hosts; a link from your self-hosted
  instance triggers a one-time prompt you can click through. That's the app's
  domain allowlist, and there's nothing to configure away.
- **Cold-launch behavior differs between the apps.** If the target app **isn't
  already running**, Bambu Studio handles the link correctly once it starts, but
  **OrcaSlicer only opens to its home screen** — its handoff event arrives
  before it's ready to receive it (an upstream macOS issue). Launch OrcaSlicer
  first, then click the link, and it works. Bambu Studio also needs its network
  agent loaded before it can pull the model.

The two apps register different URL schemes and parse the links differently, so
Print Vault builds a different link for each — that complexity is handled for
you; you just click the button.

## Push from slicer

"Open in slicer" sends a file **out**. **Push from slicer** brings it back: the
Print Vault plugin for OrcaSlicer recognises the model you have open and sends
the **project** back to it as a new revision — the process settings, the
filaments and their colours, where the objects sit on which plate. The manual
version of this is download, change, save, edit the model, re-upload; the
plugin is one button instead.

It uses OrcaSlicer's own plugin system, so there is no modified slicer build —
but that system is new: you need **OrcaSlicer 2.5 (nightly) or newer**. On
2.4.x, Bambu Studio or PrusaSlicer, the same file works as a post-processing
script with less magic (see *Older slicers* below).

### Setting it up

Once per machine, not once per model.

1. Go to **Settings → Push from slicer** and create a token, naming the machine
   it is for ("Workshop laptop"). **Copy the config it shows you right away** —
   the token is stored hashed and cannot be displayed again.
2. In OrcaSlicer, open **Plugins → Install local plugin** and choose
   `orca_print_vault_plugin_any.py` from the `orca-plugin/` folder of the Print
   Vault repository.
3. Run **Plugins → Sync with Print Vault → ▷ Run** and paste the instance URL
   and token into **Connect**, which checks them before saving. OrcaSlicer asks
   for permission the first time the plugin uses the network or reads a file;
   that is its own audit prompt, and the answer is remembered. (The
   capability's **Config** tab takes the same values, but OrcaSlicer saves a
   plugin's config with your *print profile* — so a token entered there is
   moved into the plugin's own folder the first time it runs.)
4. Optional: to have every slice queue a sync for you, switch to **Advanced**
   mode, select **Push sliced file to Print Vault** under **Print Settings →
   Others → Slicing Pipeline Plugin**, and save the profile. OrcaSlicer only
   runs a slicing plugin for profiles that name it, and it is per profile.
   Skipping this changes nothing except that you open the window yourself.

Now open a file from a model, change whatever you came to change, and run
**Plugins → Sync with Print Vault** (pin it to the Actions Speed Dial and it is
one click from the plate). The window names the project on the plate, the model
it belongs to, and how recently OrcaSlicer checkpointed it; **Update the
model's file** sends it.

Nothing has to be exported, and the project does not have to be sliced: what
the plugin reads is the crash-recovery checkpoint OrcaSlicer keeps of the open
project (**Preferences → Auto backup**, on by default, rewritten every few
seconds), merged with the file you opened — so the `.3mf` in the catalogue ends
up as a complete project written by OrcaSlicer itself, under its own name.

The same window also has an **Exported files** list, which pushes a sliced file
straight out of your export folders. That is the fallback for a project with no
checkpoint to read.

### Things to know

- **A sync is as current as the last checkpoint.** OrcaSlicer rewrites its
  project checkpoint a few seconds after you change something, so the window
  shows its age ("8 s ago") and, when there are changes newer than it, waits
  for the next one before pushing. If you would rather not rely on that, save
  the project (⌘S / Ctrl+S) first — that writes the same state to the file the
  sync is built on.
- **Automatic syncs need a profile setting.** A slice only queues a sync once
  the print profile lists the plugin (step 4 above). The plugin's
  **Diagnostics** tab records every export it saw — if nothing is there, that
  is why. Syncing from the window never depends on it.
- **Multi-plate projects are one sync.** Slicing 18 plates fires the plugin 18
  times, and all of them describe the same project: you get one card with one
  button, and one new version of one file — not eighteen revisions. Every
  plate's print time and filament weight is read out of the pushed project.
- **A just-opened project has nothing to sync yet.** OrcaSlicer writes its
  first snapshot a few seconds after you change something, so the window says
  so rather than pretending the setting is off. Change anything on the plate
  and it appears.
- **Where a project has no checkpoint at all** — auto backup switched off, or
  the file you opened has since been moved or deleted — nothing is pushed, and
  the plugin says which of the two it is. A plate of raw G-code on its own is
  not something the catalogue can use, so it is never uploaded; use *Exported
  files* to push an exported project instead.
- **A partly sliced project keeps both numbers.** Slice one plate of an
  18-plate project and the file still reads "18 plates", with its estimate
  marked "for 1 of 18 plates" — the prediction is real, it just does not cover
  the rest.
- **Nothing is pushed without you.** By default a slice is queued and waits for
  your answer. Tick *always* for a model, or switch the plugin to
  **automatic**, and future slices of that model upload silently — but only
  when the match is an exact one.
- **How it knows which model.** It hashes the file you opened and asks the
  catalogue. Since the catalogue served those exact bytes, the match is
  normally certain — including when your browser saved it as
  `fuselage(7).3mf`, which changes the name but not the contents. Failing
  that it tries the name (with any `(7)` stripped) and the design it was
  imported from, and you can always **search for a model by name** in the
  plugin's window. Whatever you pick is remembered for that project, so it
  asks once.
- **Files uploaded before content hashing existed have no hash**, and a null
  hash never matches — so an older catalogue resolves by name or search until
  you run `npm run db:backfill-hashes` once (see
  [Development](/development#database)).
- **A push never breaks your slice.** If the server is unreachable or the token
  was revoked, the plugin reports it and gets out of the way — your slicing and
  printing carry on.
- **Names are kept.** A push says which file it is a new revision of, so the
  model keeps `Bracket.3mf` rather than gaining a row named after a slicer
  temp file. Re-slicing the same plate revises that file rather than piling up
  near-identical copies. The previous
  version stays in the model's [history](/features/versioning) and can be
  restored.
- **Estimates come from your slicer, not ours.** A synced project carries the
  per-plate print time and filament weight OrcaSlicer predicted, so they are
  shown **without** the `~` that marks a server-side estimate, and the printer,
  plate and preset names ride along with it.
- **The G-code is not uploaded**, because the project is enough to re-slice
  from and a sliced plate runs to hundreds of MB. If you do want the stored
  file to be printable as it stands, tick *Put the sliced G-code inside the
  .3mf* in the plugin — it is then embedded in the project the way
  OrcaSlicer's own **Export all plates sliced file** writes it, rather than
  becoming a separate file on the model. You can still push a `.3mf` (including
  a `.gcode.3mf`) by hand from the *Exported files* list.
- **Your push token never travels in a project file.** OrcaSlicer keeps plugin
  settings in the print config, which is saved with your profile and written
  into every project you export — so the plugin keeps the token in its own
  folder, and strips that section out of every file it pushes.
- **Tokens are revocable, and push-only.** A token can add file revisions to
  models — the same editing access you already have — but cannot delete
  anything or sign you in. Revoke one from Settings → Push from slicer the
  moment the machine holding it is out of your hands.

### Older slicers

On OrcaSlicer 2.4.x, Bambu Studio and PrusaSlicer there is no plugin system.
The same file doubles as a post-processing script: store your connection once
with `--url … --token … --save --check`, then add it under **Print Settings →
Others → Post-processing Scripts**. It cannot ask you anything or see which
project is open, so it matches the sliced file by name and pushes only when
exactly one model matches. Those slicers still keep a project checkpoint, so
`--sync` pushes the project from the command line instead of a G-code file.
Full instructions are in `orca-plugin/README.md`.
